## Architecture
- Client entrance uses real Supabase Auth with HttpOnly server cookies. Operational numbers are read from Baserow table 511, exclusively filtered by the server-verified, confirmed account email. Independently validate every returned row's ownership and return only client-visible fields. Keep BASEROW_API_TOKEN server-only. Number submissions are prepared directly through the Supabase astros-submit-number Edge Function and Baserow API. Name/email come from verified Supabase identity. Only new or EXCLUIDO numbers incur the configured fee; all other supported existing statuses resend free. Supabase service jobs enforce a unique request ID and block overlapping writes. Protocol-v2 operations use a durable reconciliation queue, leased dispatch and a dedicated Baserow astros_solicitacao_id text field. A cron worker verifies exact receipt, owner and phone; it never replays uncertain writes. Refund only proven pre-dispatch failures or definite write rejection, never absence alone. Unresolved cases enter admin review after 12 checks. Legacy protocol-v1 jobs remain manual. Activation requires reconciliation SQL, cron/Vault scheduling, ASTROS_RECONCILE_SECRET and ASTROS_BASEROW_WRITE_TOKEN; a recent worker heartbeat and matching secret are required before charging. No n8n or Google Sheets dependency. Brazil keeps local DDD+number; international numbers use +DDI with selected-country validation on client and Edge Function. New and EXCLUIDO renewals write nacional for Brazil or internacional - <selected country name in Portuguese> in Baserow observacoes; free resends preserve existing observations. Do not add request markers to that field. Additional countries live in astros_custom_countries with authenticated read/admin-only CRUD RLS. Custom country IDs never authorize browser-supplied DDIs: the Edge Function must look up the current saved DDI before reservation. All standard-list DDIs and duplicate additional DDIs are forbidden for new/edited custom countries. Exclude the edited record itself from duplicate checks. Supabase enforces a unique custom DDI index and a check against the pinned standard DDI list; never delete existing country records automatically to install these constraints.
- The /admin area uses Supabase Auth on the server and painel_de_desbanimento.tipo_usuario keyed by authenticated UUID. Every administrative handler must call requireAdmin. Never authorize from localStorage or user-editable metadata.
- Legacy demo modules are unused by operational pages. Never reintroduce simulated records or balances into client routes.

- Route layouts and breadcrumb titles must follow the presented route matches (useMatches), never the requested location while navigation is pending. Public entrance/admin pages must never be rendered inside the client sidebar layout during login/logout transitions.

- Submission UI uses one Enviar número action: authenticated quote and submit run automatically with the same request UUID. Paid submissions need live Supabase balance >= configured fee; insufficient funds show recharge CTA and block before writes. Free resends remain possible at zero balance. Keep the atomic SQL balance guard and never rely on a cached client wallet to authorize a debit.

- Support settings are admin-only mutations through authenticated RPCs. Never execute pasted widget snippets: extract and validate HTTPS baseUrl + websiteToken. HMAC keys stay in astros_support_private with no client SELECT grants; identity RPC derives UUID/name/confirmed email from authenticated Supabase records. WhatsApp is a separate contact number and never updates profile or service numbers. Load SDK only after signed identity/contact preparation. Reset/hide chat on logout or account change, and prevent stale asynchronous opens. Do not enable mandatory identity validation on a shared Chatwoot inbox without adapting other sites that use it.

- Support bridge Edge Function authenticates confirmed user before loading service-role-only private config. Search Chatwoot by server-verified exact email; reject ambiguous/incomplete results and never silently create after API failure. Reuse existing contact identifier, name and phone; sign chosen identifier server-side, not a browser-provided identifier. Callback number belongs in astros_whatsapp_retorno, never overwrite legacy WhatsApp contact phone. API token/account ID configured by admin atomic RPC; private tokens must never appear in responses/logs.

- Rows containing SIM não aprovisionado remain historical and are hidden from client lists/counts/exports. Block the old email from resubmitting. Ignore retired rows for another confirmed email and create a charged new row; never update or delete retired rows. Active rows still enforce ownership and duplicate checks.

- Embedded card payments use the official Card Payment Brick with only a public key exposed. Never collect or persist PAN/CVV. Authenticated Edge derives owner/email/amount from verified identity and saved order; only token, installments, issuer and identification may come from the SDK. Service-only astros_claim_card_payment locks a SHA-256 fingerprint for one immutable attempt per order. Identical retries use the same provider idempotency key and body; changed attempts are blocked while uncertain. Reconcile the official payment before crediting through the existing atomic RPC. Legacy link orders remain readable. Bank 3DS challenges use Status Screen Brick and secure provider response fields; unmount SDK instances on navigation/account/order changes. Do not claim live card validation before SQL/function deployment, public-key setup and a controlled user test.

- Manual wallet credits require server requireAdmin and database astros_is_admin checks. Add to the existing balance atomically through astros_credit_client with a stable request UUID, row lock, audit record and wallet movement. Never simulate provider approval or overwrite the current balance. Clients cannot write manual credits or read the private audit.

- Client API defaults to blocked. Admin-only RPC grants account permission; keys are random and stored as SHA-256 hashes with no authenticated table reads. Service-only authentication checks confirmed Auth identity, banned accounts and 60/minute per-user limit. Key API cannot invoke admin reconciliation. Reuse the existing submission transaction/UUID rules for API sends; ownership always comes from verified key identity. Never log or embed keys in URLs or public client integrations.

- API diagnostics log only authenticated call metadata with server-derived owner, whitelisted operation/state/error categories and sanitized number/country/UUID. Never store key, headers, full payload or raw internal errors. Logging failure must not alter submission outcome. Client log queries/RLS enforce own UUID; admin queries requireAdmin. Retention/cap affects only astros_api_logs (30 days, 5,000/account), never financial or idempotency records.

- Legacy client import is admin-only at the application server and Edge Function, with service-only SQL RPCs validating the actor. Exclude eudezioj@gmail.com at every layer. Only import name/email/WhatsApp/Recarga; source ID is a stable deduplication key. Never import or persist legacy passwords/tokens in code or logs. Preserve all pre-existing Auth accounts; resume only accounts carrying the matching service-written app_metadata import ID. Credit and audit atomically with a durable completed marker; zero balances are valid, retries never re-credit completed or reversed entries. No recovery emails are automatically sent during import. Never upload a real customer CSV into git.

- Administrative password contingency uses requireAdmin, verified confirmed Auth identity and client-only target checks in service RPCs. Never reset self/admin accounts. A service-only marker in app_metadata requires a different new password before panel use; editable user_metadata cannot authorize its removal. Auth password changes clear the marker through the narrowly scoped SQL trigger. Guard application operations, client API authentication and JWT Edge operations until change. Preserve stable request IDs and credential-bound private HMACs for uncertain resets; reconcile the Auth marker instead of replaying writes. Audit only projected administrator/target/reason/time/state; never expose passwords or HMACs in UI or logs.
